# Migrate from deployment.yaml SMTP

:::warning[Breaking change]
The `email.smtp` block in `deployment.yaml` has been removed. <ProductName /> no longer reads it, and a deployment that still carries it sends no email. Email is delivered through an **email provider**, a connection you manage from the Console or the connections API.

See [Configure an Email Provider](../../notifications/email-providers).
:::

## Why This Changed

The `email.smtp` block configured one mail server for the whole deployment. It was read once at startup, so every change needed a server restart, the password sat in plaintext in a configuration file, and every flow that sent email had to use the same server.

An email provider is a stored connection instead. It can be created and changed at runtime, its password is encrypted at rest and never returned by the API, and each email step in a flow chooses which provider sends it.

## Migrate an Existing Deployment

There is no automatic migration: nothing carries an `email.smtp` block over to a provider, and an email step without a provider fails rather than falling back to a deployment-wide default. Migrate before you upgrade, or email-dependent features (email OTP, magic link, password recovery, user invitation) stop working.

1. Create an email provider from your existing SMTP settings, as described in [Configure an Email Provider](../../notifications/email-providers). Use the mapping below.
2. Open each flow with an email step and select the provider under **Email Provider**. The step now requires one.
3. Remove the `email.smtp` block from `deployment.yaml`.

On Kubernetes, also remove `configuration.email` from your Helm values, along with the SMTP password secret it referenced. The chart no longer renders the section or injects `SMTP_PASSWORD`.

### Property Mapping

| Removed `deployment.yaml` property | Email provider field |
| :--- | :--- |
| `host` | **Host** |
| `port` | **Port** |
| `from_address` | **From address** |
| `username` | **Username** |
| `password` | **Password** |
| `enable_start_tls: true` | **Transport security**: `STARTTLS` |
| `enable_start_tls: false` | **Transport security**: `None` |
| `enable_authentication` | **Authentication method** |

Set **Authentication method** to `Username and password` if the removed block enabled authentication and configured a username, and to `None` otherwise. A block with a host but no username becomes a provider that sends no credentials, rather than one that claims to authenticate with nothing to present.

Email providers also support implicit TLS (SMTPS, usually port 465), which the `deployment.yaml` configuration could not express. They also carry an optional **Sender name**, shown beside the address in the `From` header.
